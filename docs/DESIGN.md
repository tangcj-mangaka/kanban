# 驴看板 设计文档

> 状态：待评审
> 日期：2026-08-12

---

## 1. 项目概述

一个个人用的看板应用，覆盖 **Windows 桌面端**和 **Android 手机端**，数据在设备间实时互通。

与经典看板（Trello 式的固定列）不同，本项目的看板是一块**自由画布**：卡片可以随意摆放和拖动，没有列的概念。分类完全依靠**标签**，另有一个按标签自动分列的**分组视图**用于俯瞰。

### 1.1 核心原则

**本地优先（Local-first）**。每台设备持有一份完整数据，离线时可以完整地增删改查。同步是"有网就顺手做一下"的后台行为，不是使用的前提。服务端不在线不影响任何设备的正常使用。

### 1.2 部署形态

服务端跑在用户随身携带的 Windows 工作笔记本上，**仅局域网**，暂不上公网。

```
┌─────────────────────────────────────────┐
│  Windows 笔记本（随身携带）              │
│  ┌───────────────────┐                  │
│  │ kanban-server.exe │ 托盘常驻，开机自启 │
│  │  SQLite + 附件目录 │                  │
│  └─────────┬─────────┘                  │
│            │ 127.0.0.1                  │
│  ┌─────────▼─────────┐                  │
│  │    kanban.exe     │ 纯客户端          │
│  └───────────────────┘                  │
└────────────┬────────────────────────────┘
             │ 局域网 WebSocket + HTTP
      ┌──────┴───────┐
      │              │
┌─────▼─────┐  ┌─────▼─────┐
│ 家里台式机 │  │ Android   │
│ kanban.exe│  │ kanban.apk│
│  纯客户端  │  │  纯客户端  │
└───────────┘  └───────────┘
```

所有看板 app 都是**纯客户端，完全对等**，没有模式分支。服务端是独立进程，职责单一。

### 1.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 多用户 / 权限系统 | 单人使用 |
| 公网访问 | 当前不需要；架构已预留，换个部署位置即可 |
| 协同编辑（CRDT） | 成本过高；用"正在编辑"提示缓解 |
| 卡片间连线 / 依赖关系 | 超出范围 |
| 截止日期 / 提醒 / 优先级 | 按设计这些都由标签表达 |
| TLS 加密 | 局域网 + 个人使用；见 §9.4 |

## 2. 术语

| 术语 | 含义 |
|---|---|
| **看板（Board）** | 顶层容器，一块无限画布。可以有很多个 |
| **卡片（Card）** | 看板上的一个条目，有坐标，可自由摆放 |
| **标签（Tag）** | 卡片的分类手段。**板内专属**，不跨看板共用 |
| **画布视图** | 看板的主视图，卡片按坐标自由摆放，可拖动。**唯一的编辑主场** |
| **分组视图** | 按标签自动分列的透视图。**只读式**——可编辑内容，但不能拖动卡片 |
| **干草仓库（Haystack）** | 归档区。每个看板一个 |
| **Op** | 一次原子的字段修改。同步的最小单位 |

## 3. 数据模型

### 3.1 真相源：操作日志（Op Log）

整个系统的真相源是一张**只增不改**的操作日志表。所有的物化表都是它回放出来的读视图。

这样设计带来三个好处：
- 同步协议极简：客户端只需说"给我 seq 大于 N 的所有 op"
- 离线队列天然支持：未同步的 op 就是本地待发队列
- 字段级 LWW 天然实现：同一 (entity_id, field) 上，seq 最大的 op 生效

```sql
CREATE TABLE op (
  seq        INTEGER PRIMARY KEY,  -- 服务端分配的全局递增序号（权威排序依据）
  op_id      TEXT NOT NULL UNIQUE, -- 客户端生成的 UUID，用于去重
  board_id   TEXT NOT NULL,        -- 便于按板同步和清理
  entity     TEXT NOT NULL,        -- board | tag | card | card_tag | attachment | comment
  entity_id  TEXT NOT NULL,
  field      TEXT NOT NULL,        -- 字段名
  value      TEXT,                 -- JSON 编码的值，NULL 表示置空
  device_id  TEXT NOT NULL,
  wall_ts    INTEGER NOT NULL      -- 客户端本地时间，仅用于显示，不参与排序
);

CREATE INDEX idx_op_entity ON op(entity_id, field, seq);
CREATE INDEX idx_op_board  ON op(board_id, seq);
```

**关键点：排序权威是 `seq`，不是时间戳。**

设备之间时钟能差好几秒，用本地时间判断先后会出玄学 bug。既然只有一个服务端，就让服务端发全局递增序号——谁的 op 先到服务端谁的号小，绝对可靠，彻底绕开时钟同步问题。`wall_ts` 只用来显示"3 分钟前"这类信息。

客户端本地未同步的 op，`seq` 暂为 NULL，按本地插入顺序排队。服务端确认后回填真实 seq。

### 3.2 物化表（读视图）

物化表由 op 回放生成，供 UI 查询。每次应用 op 前先查该字段当前的 seq，只有更大的 seq 才覆盖。

```sql
-- 字段版本表：记录每个字段当前生效的 op seq
CREATE TABLE field_seq (
  entity_id TEXT NOT NULL,
  field     TEXT NOT NULL,
  seq       INTEGER NOT NULL,
  PRIMARY KEY (entity_id, field)
);

CREATE TABLE board (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL DEFAULT '',
  color      TEXT,                    -- 列表页的封面色
  sort_order REAL NOT NULL DEFAULT 0, -- 列表页排序，小数序
  created_at INTEGER NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE tag (
  id         TEXT PRIMARY KEY,
  board_id   TEXT NOT NULL,
  name       TEXT NOT NULL DEFAULT '',
  color      TEXT NOT NULL,           -- 预设色板的 key
  sort_order REAL NOT NULL DEFAULT 0, -- 决定分组视图的列顺序
  deleted    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE card (
  id         TEXT PRIMARY KEY,
  board_id   TEXT NOT NULL,
  title      TEXT NOT NULL DEFAULT '',
  body       TEXT NOT NULL DEFAULT '', -- Markdown 源文
  color      TEXT,                     -- 预设色板的 key，NULL 为无色
  x          REAL NOT NULL DEFAULT 0,  -- 画布坐标
  y          REAL NOT NULL DEFAULT 0,
  width      REAL NOT NULL DEFAULT 260,-- 可拖调；高度按内容自适应
  z          REAL NOT NULL DEFAULT 0,  -- 重叠时的层级，小数序
  collapsed  INTEGER NOT NULL DEFAULT 1, -- 画布上是否折叠
  archived   INTEGER NOT NULL DEFAULT 0, -- 是否在干草仓库
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0
);

-- 卡片-标签关系：每条关系独立记录（见 §3.4）
CREATE TABLE card_tag (
  id      TEXT PRIMARY KEY,           -- 稳定 ID = hash(card_id + tag_id)
  card_id TEXT NOT NULL,
  tag_id  TEXT NOT NULL,
  deleted INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE attachment (
  id         TEXT PRIMARY KEY,
  card_id    TEXT NOT NULL,
  hash       TEXT NOT NULL,   -- 文件内容的 SHA-256，即存储文件名
  thumb_hash TEXT,            -- 缩略图的 hash（仅图片）
  filename   TEXT NOT NULL,   -- 原始文件名（显示用）
  size       INTEGER NOT NULL,
  mime       TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE comment (
  id         TEXT PRIMARY KEY,
  card_id    TEXT NOT NULL,
  body       TEXT NOT NULL,   -- 只增不改，发表后不可编辑
  device_id  TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0
);
```

### 3.3 删除一律用墓碑

**不做物理删除。** 否则会出现：手机删了卡片、电脑同时改了它 → 同步后卡片"复活"。

删除记作 `deleted = 1` 的一次普通字段修改，参与同样的 seq 比较。删除和编辑竞争时，seq 大的赢。

墓碑记录在超过 **90 天**后由服务端清理，客户端下次同步时一并清除。

### 3.4 集合字段必须拆成独立记录

这是一个必须避开的坑。

标签和附件都是**集合**。如果把整个集合当一个字段做 LWW，会出事：

> 你在手机上给卡片加了标签 a，同时在电脑上加了标签 b
> → 整集合 LWW，后写的赢
> → **有一个标签消失了**

所以集合里的**每个成员是一条独立记录，各自 LWW + 各自墓碑**。加 a 和加 b 是两条互不相干的 op，两个都保得住。

`card_tag.id` 用 `card_id + tag_id` 的稳定哈希而非随机 UUID——这样两台设备各自添加同一个标签时，产生的是同一条记录的两个 op，天然幂等，不会变成两条重复关系。

### 3.5 排序一律用小数序（Fractional Index）

卡片 z 层级、标签顺序、看板顺序，都用 `REAL` 类型的小数序号，而不是整数下标。

插到 A(1.0) 和 B(2.0) 中间就是 1.5。这样每次调整只改**一条记录的一个字段**，LWW 直接生效，不会因为"重排整列"导致冲突爆炸。

当相邻两数差值小于阈值（浮点精度不够）时，本地静默重新均匀分配一次。

## 4. 同步机制

### 4.1 总体流程

```
用户操作
  ↓
① 立刻写本地 SQLite（物化表 + 本地 op 队列）
  ↓
② UI 立即刷新（乐观更新，0ms，不等网络）
  ↓
③ 把 op 发给服务端（如果在线）
  ↓
④ 服务端分配 seq，落库
  ↓
⑤ 服务端广播给所有其他在线客户端
  ↓
⑥ 其他客户端应用 op，UI 刷新
```

局域网内全程 **20~80ms**，手上松开，另一端基本同一瞬间就动了。

离线时停在 ①②，op 攒在本地队列。重连后自动补发，服务端按到达顺序分配 seq。

### 4.2 连接与增量同步

```
客户端连上 WebSocket
  → 发送 HELLO { device_id, token, last_seq }
  → 服务端回 SYNC { ops: [...] }        // 所有 seq > last_seq 的 op
  → 客户端应用，更新 last_seq
  → 客户端补发本地队列里未同步的 op
  → 进入实时推送状态
```

如果客户端的 `last_seq` 早于服务端最近一次压缩点（见 §4.5），服务端回 `SNAPSHOT_REQUIRED`，客户端走全量快照重建。

### 4.3 协议消息

WebSocket 上走 JSON。

**客户端 → 服务端**

| 消息 | 载荷 | 说明 |
|---|---|---|
| `HELLO` | device_id, token, last_seq | 建连握手 |
| `PUSH` | ops[] | 提交一批 op |
| `EDITING` | card_id, active | 进入/退出卡片编辑态 |
| `PING` | — | 心跳，30s 一次 |

**服务端 → 客户端**

| 消息 | 载荷 | 说明 |
|---|---|---|
| `SYNC` | ops[], server_seq | 增量补齐 |
| `ACK` | op_id → seq 映射 | 确认 PUSH，回填 seq |
| `BROADCAST` | ops[] | 其他设备的改动 |
| `EDITING` | card_id, device_name, active | 转发编辑态 |
| `SNAPSHOT_REQUIRED` | — | 要求全量重建 |
| `ERROR` | code, message | 错误 |

### 4.4 几条重要约束

**拖动过程中不发同步消息，松手才发一次。** 否则局域网里会被拖动轨迹的消息刷爆。画布拖动、宽度调整、缩放，都遵守这一条。

**正文编辑要防抖。** 打字时不是每个字符都发 op，停止输入 500ms 或失焦时才提交一次。

**批量操作打包成一批 op 发送。** 例如"清空干草仓库"可能涉及几百张卡，必须一条消息带一批 op，不能发几百条消息。

**评论不参与 LWW。** 评论只增不改，每条是独立记录，只有"发表"和"删除"两种 op，天然无冲突。想改内容就删了重发。

### 4.5 ACK 回来时必须重放该字段

「未确认的 op 压过已确认的 op」这条规则本身是对的，但**单独用会丢更新**：

```
本机：待发 op P 改字段 F，已在本地生效
远端：另一台设备也改了 F，服务端给它分配 seq = 105
本机：先收到 105 的广播 → 按规则「未确认的赢」→ 105 被丢弃
本机：随后收到自己的 ACK，P 拿到 seq = 101
结果：本机认为 P（101）生效，但正确答案是对方的（105）
```

**修法**：ACK 回来时不能只把 seq 填进去，必须对受影响的 `(entityId, field)`
**从 op log 重放一遍**，重新裁定谁赢。

这之所以可行，是因为一条 op 即使当时没被写进物化表，**也一直存在 op log 里**——
op log 是真相源，物化表只是读视图。重放就是回到真相源重新求值。

定序的 SQL 表达（最后一行就是赢家）：

```sql
SELECT * FROM op WHERE entity_id = ? AND field = ?
ORDER BY (seq IS NULL) ASC,  -- 已确认的在前，未确认的在后
         seq ASC,            -- 已确认的之间比 seq
         local_seq ASC       -- 未确认的之间比本地顺序
```

所以写入路径分两层：

| 路径 | 做什么 |
|---|---|
| 收到 op | 先入 op log（**永远入**），再用增量比较决定是否更新物化表（快路径） |
| 收到 ACK | 回填 seq，然后重放受影响字段，重新裁定 |

增量比较只是优化；正确性由「op log 永远完整」+「ACK 时重放」保证。

### 4.6 Op Log 压缩

op 表只增不减，需要定期压缩。个人使用量下这不是急事——一天几十上百个 op，一年几万条，SQLite 毫无压力——但要留好机制。

当 op 数超过 **10 万**时，服务端执行压缩：
1. 对每个 (entity_id, field) 只保留 seq 最大的那条 op
2. 记录本次压缩点 `compaction_seq`
3. 此后 `last_seq < compaction_seq` 的客户端连上来时，返回 `SNAPSHOT_REQUIRED`，走全量重建

### 4.7 正文并发编辑

两端同时改同一段长正文，字段级 LWW 会整段丢掉一方的改动。真正的协同编辑需要 CRDT，对个人项目太重，**不做**。

但有一个很便宜的缓解手段：局域网是实时连接的，所以——

**当别人正在编辑某张卡时，你这边的卡片上显示"XX 正在编辑"。**

成本极低（一个 `EDITING` 消息），能挡掉绝大部分实际冲突。

### 4.8 离线冲突的已知行为

手机离线一整天，期间改了卡片 A；重连后，它的 op 拿到的是**当前最大的 seq**（按到达顺序），因此会**覆盖**服务端上更早的改动。

这是 LWW 的正确行为，但可能与直觉不符（"我离线时改的，凭什么盖掉后来的"）。这是选择 LWW 的既定代价，接受。

## 5. 附件系统

文件不能走 WebSocket 的 JSON 消息，需要独立的 HTTP 通道。

### 5.1 存储

服务端按**内容 SHA-256 哈希**存盘：

```
<数据目录>/files/<hash前2位>/<hash>
```

天然去重——同一张图在多张卡片里用，磁盘上只存一份。数据库里只存元数据（文件名、大小、MIME、hash）。

### 5.2 接口

| 接口 | 说明 |
|---|---|
| `POST /files` | 上传，返回 hash。已存在则秒传 |
| `GET /files/{hash}` | 下载，支持 Range 断点续传 |
| `HEAD /files/{hash}` | 探测是否存在 |

单文件上限 **100MB**，超出在客户端就拦下并提示。

### 5.3 策略

| 问题 | 决定 |
|---|---|
| 手机要把所有附件都下下来吗 | **不**。缩略图自动下载，原图/文档点击才下，下过的进本地缓存 |
| 缩略图谁生成 | **客户端**上传时顺手生成一张小图（长边 400px）一起传。服务端不装图像库 |
| 服务端离线时上传的附件 | 存本地待上传队列，卡片上显示"待同步"角标，联网后自动补传 |
| 别的设备拿不到文件时 | 显示占位符 + "服务端离线"，**不报错、不阻塞** |
| 本地缓存上限 | 手机端默认 500MB，LRU 淘汰，设置里可调 |

### 5.4 文件的延迟回收

卡片被删后，它引用的文件如果没有别的卡片在用，**不立即删除**，**30 天后**才从磁盘清理。

万一误删，至少文件还在，能捞回来。

## 6. 视图与交互

### 6.1 看板列表页（入口）

网格卡片布局，每个看板显示：名称、封面色、卡片数量、最近更新时间。

- 新建 / 重命名 / 改封面色 / 删除看板（删除走强确认 + 墓碑）
- 拖动排序
- 顶部：**全局搜索框** + **服务端连接状态指示**（在线 / 离线 / 同步中）

连接状态是常驻的，用户随时知道自己现在是不是离线在用。

### 6.2 画布视图（桌面端默认）

**唯一的编辑主场。**

- **无限画布**，淡网格点背景
- 缩放：滚轮 / `Ctrl` + 滚轮；平移：空格拖拽 / 中键拖拽 / 触控板双指
- **双击画布空白处 = 在那个位置新建卡片**（最自然的新建方式）
- 拖动卡片时轻微放大 + 阴影加深，松手带弹性回落
- 拖动或点击卡片时自动提到最前（改 `z`）
- 卡片右下角可拖调宽度，高度按内容自适应
- 工具栏：缩放比例、`适应全部`（缩放到能看见所有卡片）、**`整理`**（一键把散乱卡片自动排成网格）

**画布上的卡片长这样：**

```
┌──────────────────────────┐
│ 卡片标题                  │  ← 标题
│ 正文的前两行内容，超出的部分 │  ← 折叠态只显示 2 行
│ 会被截断显示...           │
│ ● 标签A  ● 标签B          │  ← 标签色点
│ 📎 3   💬 2          ⌄   │  ← 附件数、评论数、展开按钮
└──────────────────────────┘
```

展开（`⌄`）后在画布上显示完整正文，卡片变高。
**双击卡片**打开详情弹窗——完整编辑正文、管理标签和附件、看和发评论。

### 6.3 分组视图（手机端默认）

按标签自动分列的**透视图**。

- **看板里有多少个标签就有多少列**，不需要选。列的顺序 = 标签自身的顺序
- 末尾固定一列 **「未分类」**——不带任何标签的卡片
- 一张卡有多个标签时，会**在每个对应列里各出现一份**（是同一张卡，改一处处处变）。卡片上标出它还属于哪些列
- **不能拖动卡片**
- 默认**隐藏没有卡片的空列**，顶部一个开关可以显示出来
- 列内排序：默认**按更新时间倒序**（刚动过的在最上面）。顶部可切换为：创建时间 / 画布位置（从上到下、从左到右）/ 标题

**不能拖，但不是只读。** 在这里可以：
- 点开卡片编辑内容
- 通过标签选择器给卡片改标签（不是拖拽）
- 在某列顶部点 `+` 新建卡片，自动带上该列的标签，画布上自动找一块空地放

桌面端：横向排列，可横向滚动。
手机端：单列竖向滚动，左右滑动切换列，顶部标签页条指示当前在哪一列。

### 6.4 手机端的定位

手机上的分组视图不能拖卡片，也就是说**手机上不做卡片摆放**。这是有意的取舍：

- 手机的用途是**随时看一眼、快速改内容、快速加卡片**
- **"摆位置"是电脑上干的事**——6 寸屏上看不到全局、拖动精度差，硬做体验也不好
- 手机上仍然可以切到画布视图查看和微调（双指缩放平移、长按拖卡），只是不是默认

### 6.5 干草仓库（归档区）

每个看板有一个自己的干草仓库。

归档的卡片从**画布和分组视图里彻底消失**，只在干草仓库里能看到。卡片身上的标签保留着，哪天捞出来还是原样，画布位置也还在原地。

- 列表形式展示，按归档时间倒序
- 可搜索、可按标签筛选
- 单张「捞回看板」→ 回到原来的画布位置
- 单张「彻底删除」

**「清空全部卡片」** ——这个操作要小心处理：

| 要求 | 说明 |
|---|---|
| 强确认 | 弹窗写明「将永久删除 N 张卡片，此操作不可恢复」，需要再点一次确认。不做点一下就没的按钮 |
| 走墓碑删除 | 产生一批 `deleted=1` 的 op，同步到其他设备，其他设备的仓库同步清空 |
| 打包成一条消息 | 几百张卡不能发几百条同步消息 |
| 附件延迟真删 | 按 §5.4，30 天后才从磁盘清理，留一条后悔的路 |

### 6.6 标签管理

板内的侧边面板。

- 新建标签：名称 + 从**预设色板**选颜色
- 重命名、改色
- **拖动排序**——这个顺序决定分组视图的列顺序
- **删除标签：只解除与卡片的关联，卡片全部保留**，失去该标签的卡片变成"未分类"。删除前提示「N 张卡片将失去此标签」

### 6.7 搜索

**板内搜索**（画布/分组视图顶部）
- 搜标题 + 正文 + 评论
- 画布视图下：匹配的卡片高亮，不匹配的淡出；回车逐个跳转，画布自动平移居中
- 分组视图下：过滤显示

**全局搜索**（看板列表页顶部）
- 跨所有看板搜索，结果按看板分组
- 点击结果直接跳到那张卡片并高亮

技术上用 **SQLite FTS5** 建全文索引，中文用 trigram 分词。索引在 op 应用时增量更新。

## 7. UI 设计方向

### 7.1 基调

Material 3 设计体系，但**使用固定的种子色**而不是跟随系统取色——保证 Windows 和 Android 上观感完全一致。

- 主题：浅色 / 深色 / 跟随系统
- 主色调：靛蓝 `#4A4FD0`，只用在交互元素上，不参与卡片配色
- 圆角克制（卡片 12px，按钮 8px），阴影柔和有层次
- 画布背景用极淡的网格点，提供空间参照但不干扰

### 7.2 卡片色板 —— 方案 B「明快」（已选定）

## 8. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | **Flutter 3.x** | Windows / Android 一套代码，UI 完全自绘、两端一致，动画和拖拽手感好 |
| 状态管理 | **Riverpod** | 与 drift 的响应式查询配合好 |
| 本地存储 | **drift（SQLite）** | 类型安全 + 响应式查询，数据一变 UI 自动刷新 |
| Markdown | flutter_markdown 渲染 + 自定义工具栏 | 见 §8.1 |
| 服务端 | **Dart + shelf + shelf_web_socket** | 与客户端同语言，模型和协议代码直接复用 |
| 服务端存储 | sqlite3（Dart 包） | 与客户端同一套 schema |
| 服务端分发 | `dart build cli` | 一个自带依赖的目录，**目标机器不用装任何运行时** |

### 8.1 关于正文格式

用 **Markdown**：存的是纯字符串（同步最简单），显示时渲染。配一个工具栏（加粗 / 列表 / 代码块按钮，点了自动插符号），不会 Markdown 的人也能用。

**不做富文本编辑器**——Flutter 上那些包体验参差，而且富文本存的是一大坨结构化 JSON，和字段级 LWW 配合很差（整个文档一个字段，覆盖粒度过粗）。

### 8.2 工程结构

```
kanban/
├── .github/workflows/ # Windows 云端构建
├── packages/
│   ├── shared/        # 数据模型 + 同步协议定义（客户端服务端共用）
│   ├── app/           # Flutter 客户端（Windows + Android）
│   └── server/        # Dart 服务端
├── design/            # 设计资产
└── docs/
    └── DESIGN.md
```

### 8.3 服务端的分发形态

`sqlite3` 3.x 改用了 Dart 的原生构建钩子，**`dart compile exe` 不再支持它**，
要用 `dart build cli`。产物不是单个可执行文件，而是一个目录：

```
bundle/
├── bin/server.exe
└── lib/sqlite3.dll
```

也就是说「双击一个 exe 就跑」做不到了，实际形态是**解压一个文件夹、双击里面的
exe**。对 Windows 应用这完全正常（exe 旁边放一个 DLL 是常态），而且关键的那条
仍然成立：**目标机器不需要装 Dart、不需要装任何运行时**。

发布时打包成 zip；以后做安装包的话，把这个目录放进去即可。

### 8.4 开发与构建的分工

**开发在 macOS 上做，Windows 的 `.exe` 由 GitHub Actions 云端产出。**

Flutter 不能在 macOS 上编译 Windows 桌面应用——依赖 MSVC 工具链，且不存在交叉编译方案。但这只是出包的限制：P1 的全部内容（画布、卡片、标签、分组视图、干草仓库、SQLite）都是平台无关的，macOS 桌面版就是完整的开发靶子。P2 的服务端是纯 Dart，在 macOS 上原生就能跑，Mac 客户端 ↔ Mac 服务端可以验证整套同步逻辑。

| 环节 | 在哪做 |
|---|---|
| 写代码、静态检查、单元测试 | Mac |
| 跑起来看效果、调交互 | Mac（`flutter run -d macos`） |
| 同步逻辑联调（P2） | Mac（客户端和服务端都在本机） |
| 出 Windows 包 | GitHub Actions（`windows-latest`） |
| 托盘常驻 / 开机自启 / 防火墙（P2） | **必须在 Windows 实机验证** |

**需要在 Windows 上实测一次的清单**（出包后逐项过）：

- 中文默认字体（微软雅黑）下的行高与字重观感
- **局域网广播的目标地址**：macOS 上必须用子网定向广播（发往
  `255.255.255.255` 不只是失败，还会把 socket 弄坏，之后连回环都发不出去），
  Windows 上受限广播才有效。两边行为不同，Windows 上要实测一次
- 滚动惯性、触控板手势
- 快捷键从 `Cmd` 换到 `Ctrl` 后有无冲突
- 窗口标题栏样式、应用数据目录位置
- 多显示器 / 高 DPI 缩放下的画布表现

## 9. 部署、配对与运维

### 9.1 服务端形态与控制面板

`kanban-server.exe` —— 控制台程序，随 `sqlite3.dll` 放在同一个目录里（见 §8.3）。

**原计划做系统托盘，改成了本机控制网页。** 原因是实打实的：Dart 的控制台
程序没有可用的托盘库（`tray_manager`、`system_tray` 都只支持 Flutter），
自己写 Win32 托盘要两百来行 FFI，而且**只能在 Windows 上验证**——在 Mac 上
开发时等于盲写。

托盘菜单该有的东西全部搬进了 `http://localhost:<端口>`：

| 原托盘菜单 | 控制面板 |
|---|---|
| 显示 IP、连接二维码 | 页面顶部，二维码是内联 SVG（离线可用） |
| 已连接设备、踢掉设备 | 设备列表，带在线状态 |
| 数据目录、立即备份 | 数据一节 |
| 开机自启 | 单独一节，开关一键切换 |
| 启停服务 | 关掉窗口即停；开机自启管长期运行 |

**所有控制接口只接受本机请求**（`remoteAddress.isLoopback`）。远端能调用
就等于绕过了配对这道门。

顺带的好处：这套东西在三个系统上都一样能用，不用为每个平台各写一遍。
真想要托盘图标的话，以后加一层壳即可，控制逻辑不用动。

### 9.1.1 开机自启

Windows 上写当前用户的 Run 注册表项（`HKCU\...\CurrentVersion\Run`），
不需要管理员权限，也不用装成服务。

直接把 exe 写进去会**每次开机弹一个控制台窗口**，所以中间垫一个 VBScript：
`WScript.Shell.Run` 第二个参数传 0 就是隐藏窗口启动。

引号转义是这里最容易翻车的地方——VBScript 字符串里的引号要写成两个双引号，
路径带空格时少一层引号就整个跑不起来，而且**只有开机时才暴露，那时人根本
不在电脑前**。所以脚本生成抽成了纯函数并单独测。

命令行也留了口子：`--install-autostart` / `--uninstall-autostart`。

### 9.2 局域网发现

**三条踩过的坑，都是实机跑起来才暴露的：**

| 坑 | 表现 | 处理 |
|---|---|---|
| macOS 沙盒缺 `network.client` | 客户端"连不上"，查不到原因 | 两份 entitlements 都补上出站与 UDP 权限 |
| 发往 `255.255.255.255` | macOS 上 `send()` 返回 0，**并且把 socket 弄坏**，之后连回环都发不出去 | 用子网定向广播；受限广播只在 Windows 上发 |
| `RawDatagramSocket` 的发送失败**不是同步抛异常** | 包在 `send` 外面的 try/catch 拦不住，未捕获的异步错误直接**把服务端进程干掉** | `listen` 必须给 `onError`；发现模块整体不能拖垮同步 |

最后一条是最值得记的：**锦上添花的功能把主功能弄崩了。**


- **主：UDP 广播自动发现。** 服务端定时在局域网广播自己的地址，客户端自动列出可用服务端
- **兜底：扫二维码 / 手动输入 IP:端口**

**一个必须处理的坑：强制走 IPv4。** 多网卡环境（WiFi + 虚拟网卡 + VMware/Hyper-V）下要正确挑选网卡，否则会广播出一个根本不通的地址。选网卡的规则：排除回环、排除虚拟网卡、优先当前默认路由所在的接口。托盘菜单里允许手动指定。

### 9.3 配对流程

服务端显示二维码，内容为：

```
kanban://connect?host=192.168.1.23&port=8765&code=A1B2C3
```

- 手机扫码 → 自动填入并连接
- 台式机 → 有摄像头可扫码，否则手动输入 IP:端口 + 6 位配对码
- `code` 是**一次性配对码**，5 分钟有效
- 配对成功后服务端签发一个长期 **device token** 存在客户端本地，之后自动连接
- 服务端可以查看已配对设备列表，随时踢掉某台

### 9.4 安全性取舍

**当前不做 TLS。** 局域网 + 个人使用，自签证书在 Android 上体验很差（要手动装信任链），收益不值成本。device token 机制足以防止同网段其他设备误连或乱连。

**已知代价**：同一局域网内如果有人主动嗅探，能看到明文数据。在家庭和办公网络下这个风险可接受。

**这条在上公网之前必须重新评估——那时 TLS 是强制的，且需要加上真正的身份认证。**

### 9.5 备份

- 控制面板「立即备份」→ 数据目录打包成 zip，放在同一个目录下
- 保留最近 7 份，超出的自动清理（不限量的话每天一备迟早填满磁盘）
- 备份里**不套旧备份**（否则每备份一次体积翻一倍），也不带 WAL 和临时文件
  （那是运行时状态，恢复时不需要，带上反而可能不一致）
- 备份和数据放在同一个目录看似没用，但它防的是误删看板、清空干草仓库、
  同步覆盖这类事故——比磁盘故障常见得多。真要防硬件故障，把 zip 拷走即可
- 自动定时备份尚未实现
- 恢复：停服务 → 解压覆盖数据目录 → 启动
- 客户端另有「导出当前看板」，可导出为 JSON（完整）或 Markdown（可读）

## 10. 开发路线

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P1** | 单机 Windows 版跑通：看板列表、画布视图、卡片增删改、标签、分组视图、干草仓库。**纯本地 SQLite，无同步** | 一个能用的单机看板 |
| **P2** | 服务端 + 同步：op log、WebSocket、字段级 LWW、离线队列、配对流程 | Windows 客户端 ↔ 服务端跑通 |
| **P3** | 附件系统：上传下载、缩略图、离线队列、缓存策略 | 图片和文档可用 |
| **P4** | Android 客户端：分组视图为主，画布视图适配触控 | 三端互通 |
| **P5** | 打磨：搜索（FTS5）、自动备份、UI 细节、动效、设置页 | 可长期使用 |

先做 P1 是有意的——把数据模型和交互在单机上验证清楚，再上同步。同步是最容易出玄学 bug 的地方，不能在需求还在变的时候动它。
